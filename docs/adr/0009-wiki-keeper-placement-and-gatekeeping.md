# 0009. Wiki 管理人の置き方と、GitHub への書き込みの門番

- Date: 2026-09-22
- Status: Accepted（ADR 0004 の「Wiki の規約を守る」の `raw/` の扱いを置き換え、「まだ決めていないこと」の一部を決める）

## Context

ADR 0004 で、Wiki 管理人は Wiki への変更を PR で出し、マージは本人と本人が使う Claude の指示でだけ行うと決めた。
Wiki 管理人の置き方（clone の持ち方、push と PR の資格、PR の出し方）と、マージの可否をどこで強制するかは決めていなかった。

調べて分かったことは次のとおりである。

- llm-wiki は GitHub の無料プランの private リポジトリで、ブランチ保護もルールセットも使えない。
  どの資格を使っても、PR を作れる資格は既定のブランチへの直接の push とマージも兼ねる。GitHub の側では PR 止まりを強制できない。
- 本人名義の token では、エージェントの PR と本人の PR を区別できず、本人がエージェントの PR をレビューすることもできない。
  GitHub App なら bot の名義で書け、token は短命で、token ごとに権限を絞れる。
- Pi は sandbox を持たず、隔離はコンテナに任せる立場である。Pi の拡張は、ツールの呼び出しを止めたり、専用のツールを足したり、
  使えるツールを出し入れしたりできる。
- llm-wiki の手順は、リポジトリのスキルに書かれている。スキルの形式は Pi と互換だが、どのスキルも本人に確認しながら進む前提で書かれている。
  PR の作成とマージは、llm-wiki の外にある本人のスキルに頼っている。
- ほぼすべての変更が、Wiki の索引とログのファイルの先頭を書き換える。並行する PR は、ほぼ必ずこの 2 つで衝突する。
- 原文を取り込むとき、原文は `raw/` に commit として入る。なつみとの会話が原文になる場合も、それが `raw/` に入る。
  ADR 0004 は `raw/` を読み取り専用としていたが、これでは取り込みができない。

## Decision

### GitHub の資格は GitHub App

- Wiki 管理人は、GitHub App の資格で GitHub に書く。PR は bot の名義で出る。
  - token は 1 時間の installation token を使う。権限は contents と pull requests に絞る。
  - App の鍵から token を発行するのは、汎用ホストのアダプタ（ADR 0007）である。
- App は本人が GitHub の画面で作る。
- 同じ App を、GitHub に書く他のエージェントにも使い回せる。

### 門番は Pi の拡張で道具を絞る

GitHub の側で強制できないので、PR 止まりと書き込みの範囲は Pod の中で強制する。

- bash には GitHub の資格を渡さない。
- push・PR の作成・マージは、fraction-agents の Pi パッケージ（ADR 0008）が出す専用のツールでだけ行う。
  - push の先は、既定のブランチ以外に固定する。
  - マージのツールは、呼び出し元が `owner` か `claude` の context でだけ出す。呼び出し元の名前は、アダプタが Pi の起動時に渡す。
- 書き込みの範囲は、push のツールが差分を見て強制する。
  - `raw/` は、ファイルの追加だけを許す。既存のファイルの変更と削除は拒否する。
  - `Permanent-Notes/` は、追加・変更・削除のすべてを拒否する。
- llm-wiki の規約は `raw/` を読み取り専用としているので、「Wiki 管理人は `raw/` に原文を追加してよい」を llm-wiki の側の規約に反映する。

### 残る穴を受け入れる

- App の鍵は、エージェントと同じコンテナにある。エージェントがその鍵のファイルを読み、自分で token を作れば、門番を迂回できる。
- この穴は受け入れる。理由は次のとおり。
  - 呼び出し元は本人・本人が使う Claude・なつみに限られ、認証で分かる（ADR 0002・0003）。
  - エージェントの閉じ込めを、なつみほど固くしないと決めている（ADR 0002）。
  - GitHub に書くエージェントは、いまは Wiki 管理人 1 つだけである。鍵を隔てる部品を 1 つのために作るより、道具を絞る門番を先に置く。
- 鍵を別のコンテナ（sidecar）に置き、エージェントのコンテナから読めなくする形は、GitHub に書くエージェントが増えたら共通の部品として作る。

### スキルはそのまま読み、確認は PR で代える

- llm-wiki のスキルを、Pi にそのまま読ませる。Wiki に固有の手順は llm-wiki に 1 つだけ置き、fraction-agents に写さない。
- スキルが頼っている PR の作成とマージは、門番の専用のツールで置き換える。
- スキルの中の本人への確認は、Wiki 管理人の AGENTS.md で上書きする。原則として確認せずに進める。事前の確認の代わりが PR である。
- 不確かなとき、矛盾があるとき、判断が怪しいときだけ、A2A の「入力待ち」で呼び出し元に聞き返す。

### clone と並行する PR

- PVC に llm-wiki の永続の clone を 1 つ置き、context ごとに `git worktree` を作る。
  - Wiki 管理人のレプリカは 1 つにする。
  - 途中で落ちた context の worktree を掃除する処理を持つ。
- 並行する PR は許す。
  - マージのツールは、最新の既定のブランチを取り込んでからマージする。
  - 索引とログのファイルの衝突は、Wiki 管理人がその場で解消する。
  - それ以外の衝突が起きたら、マージせずに呼び出し元に聞き返す。

### まだ決めていないこと

- その context の PR がマージ済み、または閉じられた後に、同じ context で書き込みを頼まれたときの扱い。実装の作業単位で決める。

## Consequences

- Wiki の変更は bot の名義の PR になり、本人は自分の変更と区別してレビューできる。
- token は 1 時間で切れるので、漏れたときに使える時間が短い。その代わり、アダプタが token を発行し直す処理を持つ。
- なつみの依頼が PR で止まること、`raw/` を追加だけにすること、`Permanent-Notes/` に触れないことは、指示ではなく道具で守られる。
  ただし、同じコンテナの鍵を使った迂回は防げない。
- 原文を `raw/` に足す取り込みを、Wiki 管理人ができるようになる。既存の原文を書き換えることはできない。
- Wiki の手順を llm-wiki と fraction-agents の二か所で持たずに済む。llm-wiki のスキルを直せば、Wiki 管理人にもそのまま効く。
- 確認を挟まずに進むので、呼び出し元の意図と違う変更が PR に積まれることがある。それを見て止めるのが PR の役目になる。
- context ごとの worktree が PVC に残るので、同じ context の再開では作業の途中から続けられる。レプリカを増やして負荷を分けることはできない。
- 索引とログの衝突は、マージのたびに Wiki 管理人の判断で解消される。解消の結果も PR に残る。

## 実装での注記（2026-09-22）

### token を発行するのは拡張

- 「App の鍵から token を発行するのは、汎用ホストのアダプタ」を改め、門番の Pi の拡張が発行する。
- 理由は次のとおり。
  - token を使うのは、pi のプロセスの中の専用のツールだけである。アダプタで発行すると、pi へ渡す経路が要る。
    環境変数で渡せば bash にも見え、別の経路を作ると、1 時間ごとの発行し直しのたびにアダプタと pi がやり取りすることになる。
  - 鍵は、どちらで発行しても同じコンテナにある。アダプタに置いても、この ADR が受け入れた穴は変わらない。
  - アダプタが GitHub を知らずに済み、汎用のままでいられる。
- bash と LLM の文脈に token が出ない、という条件は変えない。token は pi のプロセスのメモリにだけ持ち、
  git には 1 回の git のプロセスの環境変数でヘッダを渡す。pi の環境変数、ファイル、git の設定、remote の URL には置かない。

### マージ済み・閉じた PR の後の書き込み

- 「まだ決めていないこと」の、PR がマージ済みまたは閉じられた後に、同じ context で書き込みを頼まれたときの扱いを決める。
- 新しいブランチ（`<接頭辞><contextId>-2` のように番号を足す）を最新の既定のブランチから作り、新しい PR を出す。
  前回の push の後に積んだ commit だけを新しいブランチに移す。移せない（衝突する）ときは、push せずに呼び出し元に聞き返す。
- 閉じられた PR の commit は、新しいブランチに持ち込まない。閉じたのは呼び出し元がその変更を採らなかったということだからである。
- 1 つの context に 1 つの PR という形は、「開いている PR は 1 つ」と読み替える。

### 聞き返し

- 「入力待ちで聞き返す」は、Pi の拡張のツール `ask_caller` が pi の RPC の入力のダイアログを開き、
  汎用ホストがそれを Task の `INPUT_REQUIRED` に写す形で作った。呼び出し元が同じ Task に答えると、同じ prompt が続く。
