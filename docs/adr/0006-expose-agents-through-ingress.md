# 0006. エージェントは既存の Ingress でインターネットに出し、守りは認証に任せる

- Date: 2026-09-22
- Status: Accepted（ADR 0003 の「公開の範囲」を置き換える）

## Context

ADR 0003 は、エージェントを LAN の中だけに公開すると決めていた。

LAN の中だけに公開する形を調べると、次のことが分かった。

- LAN と外を分けているのはクラスタの外の firewall で、クラスタの中には境界が無い。
  LAN 向けのアドレスを選んでも、選び方によっては外に出てしまう。
- LAN の中だけでは TLS を持たない。bearer token（ADR 0003）を平文の HTTP で送ると、LAN の中で盗み見られれば token が取れる。
- 家の外にある Mac からエージェントを呼ぶ経路が無い。

クラスタには既存の Ingress がある。この Ingress は証明書を自動で扱うので TLS を持ち、ポリシーを掛けなければリクエストをそのまま通す。

## Decision

### 既存の Ingress で公開する

- エージェントは、既存の Ingress を通してインターネットに公開する。ADR 0003 の「LAN の中だけに公開する」は採らない。
- TLS は Ingress に任せる。エージェント自身は TLS を持たない。
- Ingress のホスト名などの環境に固有の設定は、このリポジトリに書かない（ADR 0010）。

### 守りは認証に任せる

- エージェントを守るのは、ServiceAccount の token と TokenReview による認証（ADR 0003）である。ネットワークの範囲では守らない。
- 依頼の受け付け、Task の取得、成果物の URI の取得のすべてに認証を掛ける。

### まだ決めていないこと

- Agent Card にも認証を掛けるか。掛けなければ、外からエージェントの存在と能力が見える。実装の作業単位で決める。

## Consequences

- 家の外の Mac からも、本人と Claude がエージェントを呼べる。
- token が TLS の上を流れるので、経路の途中で token を盗み見られる心配が減る。
- エージェントの口がインターネットから届く。認証の実装の誤りが、そのまま外からの穴になる。認証を通らない依頼を一切処理しないことが前提になる。
- 認証を通らない依頼も、TokenReview の問い合わせを引き起こす。外からの大量の依頼が apiserver の負荷になりうる。
- Agent Card に認証を掛けない場合、エージェントの一覧と能力は外から見える。

## 実装での注記（2026-09-23）

- 「まだ決めていないこと」の Agent Card の認証を決める。Agent Card には認証を掛けない。
  - 汎用ホストは、Agent Card（`/.well-known/agent-card.json`）と `/healthz` を認証なしで返す。
  - エージェントの名前・説明・スキルは外から見える。Agent Card に秘密や内部の情報を書かない（README の「汎用ホスト」）。
- 理由は次のとおり。
  - A2A の呼び出し元は、まず Agent Card を読んで、呼び出す先と呼び方を知る。Agent Card を公開の情報として扱うのが、A2A の素直な使い方である。
  - Agent Card に載るのは、設定に書いた名前・説明・スキルだけである。見えて困る情報は、書かないことで守れる。
