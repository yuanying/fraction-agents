# 0016. Gmail Agent: 本人の OAuth で Gmail を読み取り専用で読み、毎朝の一次選別をなつみに返す

- Date: 2026-10-10
- Status: Accepted（毎朝の確認・一次選別とチェックの取り決めは、末尾の「チェックを取り下げる（2026-10-10）」で取り下げた。Gmail Agent は自然な言葉の依頼に答える読み取り専用の係になった）

## Context

秘書のなつみが、本人の Gmail に届いたメールのうち、本人が知っておくべきものを毎朝まとめて伝えたい。
選別の方針は、本人が毎日の報告を見ながら、なつみとの会話で少しずつ調整できるようにしたい。

なつみは 1 つのセッションを 1 日使う。届いたメールの本文をすべてなつみに読ませると、1 日の文脈がメールで埋まる。
なつみ本体に Gmail の資格を持たせると、なつみのコンテナに置く秘密が増える。
メールは外から誰でも送れる文であり、本文に仕込まれた指示に会話の相手が促される危険もある。

そこで、カレンダー係（ADR 0014）と同じく、fraction-agents に Gmail 専用のエージェント（以下 Gmail Agent）を立て、なつみが A2A で頼む（ADR 0001）。

前提として分かっていることは次のとおりである。

- カレンダー係は、本人がカレンダーをサービスアカウントに共有する方式で動いている。
  Gmail では、Calendar のようにリソースをサービスアカウントへ共有して、Gmail API のアクセス権を与える方式は使えない。
- サービスアカウントが本人として Gmail を読むには、Google Workspace の管理者がドメイン全体の委任（domain-wide delegation）を許可する必要がある。
  個人の Gmail アカウントでは使えない。
  委任の権限はドメインのユーザー全体に及び、アプリの側で対象を 1 人に絞っても、委任そのものの範囲は狭まらない
  （[Google の OAuth 2.0 for Server to Server Applications](https://developers.google.com/identity/protocols/oauth2/service-account#delegatingauthority)）。
- 本人は、個人の Gmail と Workspace のどちらのアカウントも使う可能性がある。
- 汎用ホストは、構造のある返事（要約・節・出典）を A2A の拡張で返せる（ADR 0015）。
  なつみの側は、外のエージェントの返事を `/sources` にファイルで置き、`sources_updated` で知らせて、要約から必要な節だけを読む（natsumi の ADR 0069）。

## Decision

### 責任の分け方

Gmail Agent となつみの責任を次のように分ける。

| 責任 | 持ち手 |
|---|---|
| 本人の好み（選別の方針）の正本と、その記憶 | なつみ |
| 毎朝の依頼を始めること | なつみ |
| 報告するか、何をどう本人に伝えるかの最終判断 | なつみ |
| Gmail の資格の保管と、Gmail の検索・本文の取得 | Gmail Agent |
| 依頼に添えられた方針に沿った一次選別 | Gmail Agent |

- なつみは、依頼のたびに最新の方針を添える。Gmail Agent は方針を自分の正本として持たない。
- Gmail Agent は、選別した候補だけを構造のある返事（ADR 0015）で返す。メール本文の全文をなつみに流さない。
- なつみは返事を `/sources` に置き、`sources_updated` で扱う。短い一覧を読み、必要な候補の詳細だけを読む。
- Gmail Agent は、カレンダー係を置き換えない。カレンダー係の構成（汎用ホストと Pi パッケージの拡張、資格を係の中に閉じること）を参考にするが、認証は別に作る。

### 毎朝の確認

- なつみが、既存の定期予約で毎朝 8 時（日本時間）に依頼を始める。
  8 時は依頼を始める時刻であり、報告が届く時刻ではない。報告は処理が終わった後になる。
- 自動の報告は 1 日 1 回だけとする。緊急のメールでも、追加の自動通知はしない。
  本人が会話で確認を頼むことはできる。
- 重要なメールが無い日は本人に通知しない。チェックした結果だけを残す。
- 報告は、メールごとの短い要約、重要と判断した理由、Gmail でそのメールを開くリンクとする。
  詳しい内容は、本人に頼まれたときに確かめる。
- 一度報告したメールは、自動では繰り返さない。フォローは頼まれた場合だけ行う。

### 対象のメール

- 前回のチェック以降に届いたメールを対象とする。既読か未読かは問わない。
- 自動振り分けやアーカイブで受信トレイから外れたものを含め、受信したメール全体を対象とする。
  迷惑メール・ゴミ箱・送信済みは除く。
- 初回は直近 24 時間を対象とする。それより前のメールは、個別の検索の依頼で取り出す。
- アカウントは、初期版では 1 つだけとする。

### 好みの扱い

- 本人が会話で好みを伝えたら、なつみはすぐ方針に反映し、どう解釈したかを短く返す。確かめるのは、指示が曖昧な場合だけとする。
- 「重要じゃない」は、優先度を下げる指示として扱う。その種類のメールでも、内容が重要なら例外として候補に残す。
- 「一切報告しない」とはっきり言われた種類だけを、完全に除外する。
- 初期の方針は見落としを減らす側に寄せる。迷うメールも候補にし、本人の調整で徐々に絞る。
  広告や一斉配信を無条件にすべて報告するという意味ではない。

### 添付

- 自動のチェックで見るのは、本文と、添付の名前・種類までとする。
- 添付の中身は、本人に頼まれた場合だけ確かめる。

### 失敗したとき

- 失敗したら、自動で再試行する。それでも失敗したら、本人に短く知らせる。
- チェックできなかった期間は、次に成功したときに対象に含める。
- 次の性質は、実装の形によらず守る。
  - 同じメールを二重に報告しない。
  - 再起動や処理の途中の失敗、ページングの途中で、メールを取りこぼさない。

### 認証と権限

- 初期版の認証は、本人の OAuth の同意だけとする。個人の Gmail と Workspace のどちらでも同じ方式で動く。
  - 退けた案: サービスアカウントとドメイン全体の委任。個人の Gmail で使えず、委任の権限がドメイン全体に及ぶ。
    Workspace で必要になったら、そのとき別に判断して追加する。
- scope は `gmail.readonly` だけとする。
  Gmail Agent は、送信・既読化・ラベルの変更・削除を道具として持たない。
- OAuth の資格（refresh token など）は Gmail Agent の側だけに置く。なつみには渡さない。
- メールの本文と添付に含まれる指示は外部のデータとして扱い、命令として実行しない。

### モデル

- モデルは、ほかの係と同じ ChatGPT Plus の経路を使う。一次選別のために、メールの本文をこのモデルに渡すことを本人が了承している。

### 実装で詰める事項

次の事項は、この ADR では決めない。後続の実装で決め、必要なら ADR に追記する。

- OAuth の初回の認可をどこで行うか、認可の戻り先、refresh token の保管方式、再認可の手順。
- チェックした範囲・最後に成功した時点・報告済みのメールの記録を、Gmail Agent となつみのどちらが永続化するか。
- 再試行を Gmail Agent となつみのどちらで行うか、その回数と間隔。8 時にサーバーが止まっていた場合の追いつき方。
- 好みの記憶を依頼のときに取り出す方法。候補の一覧と詳細を返す構造化応答の中身。結果の保存期間。
- 1 回に扱うメールの件数と本文の量の上限。上限に達したときに続きをどう処理するか。
- 添付の中身を頼まれたときに扱う形式・大きさの上限と、安全な取り扱い方。
- 初期の選別方針の具体的な中身。

## Consequences

- なつみの 1 日のセッションには、メール本文の全文を一括では流さない。入るのは選別された候補の要約が中心になる。
  なつみは、最終判断に必要な候補の詳細を必要な範囲で読む。本人から詳細を頼まれた場合にも確かめる。
- 方針の正本がなつみにあるので、Gmail Agent は依頼に添えられた方針だけを見て選別する。
  方針を添え忘れた依頼では、本人の好みが反映されない。
- 一次選別でこぼれたメールは、なつみにも本人にも見えない。見落としを減らす初期方針は、このための寄せである。
- 緊急のメールでも、本人が気づくのは翌朝の報告か、本人が会話で確認を頼んだときになる。
- 本人は、Google Cloud で OAuth のクライアントを作り、Gmail API を有効にし、Gmail Agent に同意を与える手順を踏む。
  Google Cloud の OAuth 同意画面がユーザーの種類「外部」で公開ステータスが「テスト中」のままだと、Gmail の scope を求める refresh token は 7 日で切れる
  （[Google の Using OAuth 2.0 to Access Google APIs の Refresh token expiration](https://developers.google.com/identity/protocols/oauth2#expiration)）。
  この構成をとるなら、再認可の手順か公開ステータスの扱いを実装で決める必要がある。
- refresh token が漏れると、取り消すまで本人のメールをすべて読める。資格は Gmail Agent の側だけに置き、Gmail Agent には資格のファイルを読む道具を出さない。
- `gmail.readonly` なので、Gmail Agent はメールを変えられない。既読にもしないので、本人の Gmail の見え方は変わらない。
  ラベル付けやアーカイブを頼めるようにするなら、scope を広げる別の判断が要る。
- メールの本文が ChatGPT Plus の経路のモデルに渡る。
- 複数のアカウントを扱うようになったら、資格の持ち方と、どのアカウントのメールかの示し方を別に決める。
- この ADR は設計の決定であり、Gmail Agent はまだ実装されていない。利用できるようになるのは、実装と配置が終わってからである。

## 実装での決定（2026-10-10）

「実装で詰める事項」を、実装で次のように決めた。呼び出し元との取り決めの全体は `docs/gmail-agent/check-contract.md`、
本人の準備と再認可の手順は `agents/gmail-agent/README.md` にある。汎用ホストは変えていない。

### 係の作り

- 係は汎用ホストの上に作り、Gmail の道具は Pi パッケージの拡張 `gmail` に足した（カレンダー係と同じ）。名前は `gmail-agent`。
- 道具は、検索・1 通を読む・テキストの添付を読む・チェックの 5 つ（始める・次のバッチ・記録・結果・ack）である。
  送信・既読化・ラベル・削除の道具は無く、Gmail には GET だけを送る。
- Google の API は REST を直接呼び、`googleapis` などのライブラリには頼らない（カレンダー係と同じ理由）。
- pi の組み込みの道具は出さない（`defaultTools: []`）。モデルからは、資格のファイルを読む道も、任意のファイル・コマンド・ネットワークに触れる道も無い。

### OAuth の認可

- 本人が作った「デスクトップ アプリ」の OAuth クライアントで、本人の手元の端末で認可する。
  コマンド `pi-package/bin/gmail-authorize.ts` が 127.0.0.1 で戻りを待ち、`state` で偽の戻りを断り、PKCE（S256）で code を交換する。
  `access_type=offline` と `prompt=consent` で、毎回 refresh token を受け取る。
  - ブラウザの無い端末では、ポートを決めて SSH で転送する。
  - 退けた案: 係の Pod で認可し、Ingress で戻りを受ける。戻り先を外に開く必要があり、Web アプリのクライアントの秘密が係の外に要る。
  - 退けた案: デバイスの方式（device code）。Google のこの方式は Gmail の scope を許していない。
  - 退けた案: OOB（コードを貼り付ける方式）。Google が止めている。
- scope は、認可の応答と、access token を取るたびの応答の両方で確かめ、`gmail.readonly` 以外が付いていれば使わない。
- 資格（クライアントと refresh token）は、Google のライブラリの `authorized_user` の形の JSON で、モード 0600 で書き、Kubernetes の Secret にする。
  係は access token を取るたびに読むので、Secret を差し替えれば再起動なしで新しい資格を使う。
- refresh token が失効・取り消された（`invalid_grant`）ときと、Gmail が 401 を返したときは、試し直さずに再認可が要るという誤りにする。
- 「外部」で「テスト中」の 7 日の期限は、コードでは決めない。本人が「内部」（Workspace）・「本番環境」（審査なし）・毎週の再認可のどれかを選ぶ。
  それぞれの手順を README に書いた。

### チェックの永続化と責任

- 窓（どこまで見たか）・一覧のページの位置・まだ判断していない ID・判断・候補・ack で受け取った ID は、Gmail Agent が永続化する。
  一覧の位置と判断の途中を知っているのは係だけで、ここで持たなければ、失敗や再起動で取りこぼす。
  状態は係の PVC の上のファイルで、係の pi のプロセスどうしはロックのファイルで書き換えを順に行う。
- なつみは、方針の正本と、本人に何を報告したかの記録を持つ。
- チェックの「完了」と「ack 済み」を分けた。
  - 完了は、窓のメールをすべて判断し終えたこと。完了したら、次の窓はその終わりから始まる。
  - ack 済みは、なつみが報告したメールの ID（無ければ空）を知らせたこと。結果を受け取っただけでは何も報告済みにならない。
  - 退けた案: ack が来るまで次の窓を始めない。ack が 1 度失われると、次の日以降のメールが見られなくなる。
    代わりに、ack の無い完了したチェックを返事の `unacknowledgedChecks` で知らせ、なつみが ack を送り直すか候補を取り直す。
  - 退けた案: 結果を返した時点で報告済みにする。返事がなつみに届かなかったときに、報告されないまま消える。
- 依頼には `requestKey` を付ける。同じ鍵の依頼は同じチェックを返すので、なつみは失敗した依頼を同じ鍵で送り直せばよい。
- 途中のチェックは 1 つだけとする。新しい依頼が来たら、それを続け、窓の終わりを今に延ばす。窓の間に隙間ができない。
- 窓の境目では、一覧を 1 時間さかのぼって取る。遅れて届いたメールを拾い、前の窓で判断したメールは、覚えておいた ID（7 日）で除く。

### モデルにチェックを飛ばさせない

- 一次選別はモデルが行うが、進み具合は道具が決める。バッチ（10 通）は、全部のメールの判断が記録されるまで同じものが返る。
  判断が欠けた記録や、バッチに無い ID の記録は断る。完了かどうかも道具が決める。
- チェックの結果と ack の返事は、道具が保存した状態から作って返事のファイルに書く（`submit_reply` を使わない）。
  状態・件数・残りは、モデルの言い分ではなく保存した状態のとおりに届く。モデルが書くのは、候補ごとの優先度・要約・理由と、進められなかった理由（`problem`）だけである。
- Google が認可を断った後のチェックの返事には、道具が「再認可が必要」の `problem` を入れる。なつみはこれで、再試行せずに本人に知らせると決められる。

### 上限と続き

- チェックのバッチは 10 通、本文は 1 通 4000 文字まで。切ったことと続きの位置を明示し、要るときは 1 通を読む道具で続きを読む。
- 1 回の依頼で進めるのは 20 バッチ（約 200 通）までとし、超えたら途中の返事（`scanning` と残りの件数）を返す。なつみが同じ `requestKey` で続きを頼む。
  これはプロンプトの決まりで、道具では止めない。止めても、取りこぼしは起きない（進み具合は道具の側にある）。
- 返事の候補は 30 件まで（返事の取り決めの節の上限の中に収める）。続きは `offset` で頼む。要約は 400 文字、理由は 300 文字までで、超えたら切らずに書き直させる。
- 1 通を読む道具は本文を 12000 文字まで、検索は 50 通までを返す。

### 再試行

- 係の中の再試行は、Gmail と token のエンドポイントへの 1 回の要求ごとに、429 と 5xx だけを 4 回まで（`Retry-After`、無ければ 1・2・4 秒）とする。
- 依頼そのものの再試行は、なつみが行う（同じ `requestKey` で 5 分・15 分・45 分の間を空けて 3 回まで。再認可が要るときは試し直さない）。
  8 時にサーバーが止まっていたら、なつみが動き出したときに依頼する。窓が前回の完了から続くので、止まっていた間のメールも入る。
- どの失敗でも、チェックの窓と位置は進まない。

### 添付

- 添付は名前と種類で振り分け、実行できるもの（実行ファイル・スクリプト・マクロ付きの Office の文書・ディスクイメージなど）と圧縮ファイルは開かない。
- 中身を読むのは、頼まれたときに、テキストの形式（プレーンテキスト・CSV・Markdown・HTML・カレンダー・JSON）で 512 KB までのものだけで、20000 文字までを見せる。
  PDF・画像・Office の文書は、名前と種類だけを見せる。読み取りの道具を増やさず、依存も増やさないため。

### 保存期間と初期の方針

- 完了したチェックは、完了から 30 日で消す。ack で受け取った ID は 90 日、境目のための判断済みの ID は 7 日で消す。
- 初めの方針（方針の無い依頼で使う）は、係の AGENTS.md に書いた。見落としを減らす側に寄せ、迷ったら優先度を低くして候補に残す。

### 保証しないこと

- 本人への報告がちょうど 1 回になることは、この係だけでは保証できない。係は、なつみが本人に送ったかを知らない。
  二重の報告を防ぐのは、なつみが報告を記録してから ack を送ることである。

### この決定の帰結

- なつみの側に、`requestKey` の付け方、返事の `gmail-check` の JSON の読み方、報告の記録、ack の送り直しを実装する必要がある（取り決めの文書のとおり）。
- 「テスト中」のままなら、本人は 7 日ごとに再認可する。
- 1 回の依頼の上限はプロンプトで守るので、モデルが守らなければ 1 回の依頼が長くなる。取りこぼしは起きない。
- 状態のファイルが壊れたら、チェックは止まる（上書きしない）。直すか消すかは人が決める。
- 境目の 1 時間より遅れて届いたメールは、窓から漏れうる。

## チェックを取り下げる（2026-10-10）

### Context

上の「実装での決定」のとおりにチェックの取り決めを実装した後、本人が、なつみの毎朝のチェックの仕組みを取り下げた。
なつみには、Gmail Agent の頼み方を手引きに書くだけにし、好みは本人がそのときに何をしたいかとして頼む。
本人が頼むので、毎朝の依頼のようなシステムの出来事は要らない、という判断である。

Gmail Agent についての本人の決定は次のとおりである。

- 「削る。gmail agentはgmailの中身を自然言語で検索できるAgentにしたい。例えば、『今日の〜〜を中心として〜〜見たいな好みがある時の重要なメールを優先度順で返して』とか」
- 「読み取り専用のAgentで頼み方によってメールを返してくれるAgent」
- 「古いメールの検索なども頼んだらして欲しい」

### Decision

- Gmail Agent は、自然な言葉の依頼を受けて Gmail を調べて返す、読み取り専用の係とする。依頼してくるのは、本人・本人が使う Claude・なつみである。
  - 依頼に含まれる好み・重点に沿って重要なメールを選び、優先度と理由を付けて優先度順に返す。好みが無いときは、AGENTS.md の初めの方針で選ぶ。
  - 期間・差出人・件名などで探す。古いメールも、頼まれれば Gmail の検索式の期間（`after:`・`before:`・`older_than:`）で探す。
  - 特定のメールの詳細を読み、要約して答える。
- 好みは依頼ごとに書く。Gmail Agent は前の依頼の好みを覚えて使わない。好みの正本を持つ者は置かない。
- 返事は返事の取り決め（ADR 0015）の `submit_reply` で返す。メール 1 通に 1 節で、日時・差出人・件名・要点・（優先度順の依頼なら）優先度と理由・Gmail のリンクを入れる。
  本文の全体は返さない。1 回の返事は 30 通までとし、超えたら返していない件数と続きの頼み方を書く。
  1 回の依頼で一覧に取るのは 200 通までとし、全部を見られなかったときはそう書く。どちらもプロンプトの決まりである。
- チェックの取り決め一式を削る。道具（`gmail_check_begin`・`gmail_check_next`・`gmail_check_record`・`gmail_check_reply`・`gmail_check_ack`）、
  永続状態（窓・一覧の位置・判断・候補・ack の ID）と `gmail.json` の `stateDir`、取り決めの文書を削った。
- 残すもの: `gmail.readonly` だけの 1 アカウントの検索・1 通を読む・添付の名前と種類・頼まれたときだけのテキストの添付の読み取り、
  本人の手元での OAuth の認可のコマンドと、資格を係の中に閉じる境界、429・5xx の有限の再試行と、401・`invalid_grant` の再認可の誤り、
  件数・本文量の上限と、切り詰めを隠さないこと。検索の結果には、Gmail が見積もった件数を出す。
- 再認可が要るときは、係が返事の要約の 1 行目にそう書く。道具が返事に自動で入れる仕組み（チェックの返事の `problem`）は、チェックと一緒に削った。

### 取り下げた部分

上の本文のうち、次は取り下げた。履歴として本文は残す。

- 「責任の分け方」の、好みの正本と毎朝の依頼をなつみが持つこと、一次選別、`/sources` で候補の一覧を読む流れ。
- 「毎朝の確認」「対象のメール」の全体、「好みの扱い」のうちなつみが方針に反映すること、「失敗したとき」のうち自動の再試行・期間の追いつき・二重報告と取りこぼしの防止。
- 「実装での決定」のうち「チェックの永続化と責任」「モデルにチェックを飛ばさせない」「上限と続き」のチェックの部分、
  「再試行」のなつみの側の再試行、「保存期間と初期の方針」の保存期間、「保証しないこと」、「この決定の帰結」のなつみの側の実装と境目の漏れ。

### Consequences

- 毎朝の自動の報告は無い。重要なメールは、本人かなつみか本人の Claude が頼んだときに分かる。頼まれない日のメールは、誰も一次選別しない。
- 係は依頼のあいだで何も覚えないので、同じメールを別の依頼でまた返すことがある。何を本人に伝えたかを覚えるのは、頼んだ側である。
- 好みを依頼に書き忘れると、初めの方針で選ぶ。
- 係の PVC には、Gmail の道具が独自に置くものが無くなった。PVC は、ほかの係と同じくホストの Task・セッションと pi のログインの情報に使う。
- `gmail.json` の `stateDir` は、知らない項目として断る。前の版の `gmail.json` を使う環境は、`stateDir` を消す必要がある（残っていると Gmail の道具が出ない）。
- 一覧の 200 通と返事の 30 通の上限はプロンプトで守るので、モデルが守らなければ、返事の取り決めの大きさの上限で `submit_reply` が断る。
