# 0007. 汎用ホストは A2A のアダプタが context ごとに Pi を子プロセスで動かす

- Date: 2026-09-22
- Status: Accepted

## Context

ADR 0002 で、汎用ホストは Pi を headless で動かし A2A で包んだ共通の image であり、セッションは A2A の context の単位と決めた。
ADR 0001 は、A2A と SDK の版と、結果の受け取り方を実装の前に決めることにしていた。ここでそれらを具体化する。

本人は、できるだけ Pi のエコシステムに乗る形で作りたいと考えている。

調べて分かったことは次のとおりである。

- A2A の最新の仕様は 1.0（1.0.1）である。公式の JS/TS SDK `@a2a-js/sdk` は 1.0 に対応し、1.2 系が出ている。
  SDK には、Task の状態を永続化する仕組みが同梱されていない。
- Pi のパッケージは `@earendil-works/pi-coding-agent` に改名された。以前の名前のパッケージは更新が止まっている。
  最新の 0.87 には、なつみが使う API を消す破壊的な変更がある。汎用ホストはなつみのコードに依存しない。
- Pi には、JSONL で操作する RPC のモードがあり、セッションのファイルを指定して起動できる。
  Pi の公式のチャットの橋（`pi-chat`）は、会話の単位ごとに Pi のプロセスを立てる形で作られている。
- Pi の拡張として A2A の受け口を作る方式（例えばコミュニティの `pi-a2a`）もある。

## Decision

### A2A の版と SDK

- A2A の仕様は 1.0（1.0.x）に合わせる。0.3 には合わせない。
- A2A の処理には公式の `@a2a-js/sdk` の 1.2 系を使う。

### Pi の版

- 汎用ホストの Pi は、`@earendil-works/pi-coding-agent` の最新（0.87 系）から始める。
- なつみの Pi の版は、なつみの側の事情で据え置く。汎用ホストはなつみの版に合わせない。

### 汎用ホストの形

- 外側に薄い A2A のアダプタを置く。
  - アダプタは `@a2a-js/sdk` で A2A を受ける普通の Node のサーバーで、コンテナの主プロセスになる。
  - 認証（ADR 0003）と Task の管理はアダプタが受け持つ。
- アダプタは、context ごとに Pi を RPC のモードで子プロセスとして立て、その context のセッションのファイルを渡す。
  - アイドルになった context の子プロセスは落とす。同じ context の依頼が来たら、同じセッションのファイルで起動し直す。
  - 降ろすまでの時間とファイルを消すまでの期間は ADR 0002 のとおり設定で決める。
- 子プロセスの Pi は素の Pi として動き、AGENTS.md・スキル・拡張・設定は Pi 本来の探索で読まれる（ADR 0008）。
- 呼び出し元の名前など、依頼ごとに変わる情報は、アダプタが子プロセスの起動時に渡す。

### 受け口を Pi の拡張にする形は採らない

- A2A の受け口を Pi の拡張として作り、1 つの Pi のプロセスの中で context ごとのセッションを持つ形は採らない。理由は次のとおり。
  - Pi にはサーバーとして常駐するモードが無い。拡張はセッションに属するので、空のセッションを開けたままにし、
    その付属品としてサーバーを生かす形になる。コンテナの主プロセス、終了の扱い、生存の確認が、本来の主役と食い違う。
  - 1 つのプロセスにすべての context が載るので、1 つの障害がすべての呼び出し元に及ぶ。
  - 既存の実装は context の会話を独自のファイルに持ち、「1 つの context を 1 つの Pi のセッションとして再開する」（ADR 0002）形と合わない。

### 結果の受け取り方

- 最初は、ポーリングだけを出す。依頼の送信はすぐ戻し、呼び出し元は後から Task を取りに行く。
- ストリーム（SSE）は後で足す。

### contextId と Task の持ち主

- contextId はサーバーだけが採番する。呼び出し元が指定した contextId は、その呼び出し元の既存の context に限って受け付け、それ以外はエラーにする。
- Task と context は、呼び出し元（認証で得た ServiceAccount の名前）ごとに分ける。他の呼び出し元の context は続けられず、その Task も見えない。
- 外から来た contextId を、そのまま Pi のセッションのファイル名にはしない。

### Task の状態の持ち方

- Task の状態は SQLite に書き、エージェントの PVC に置く。Pod が再起動しても、呼び出し元は同じ Task を取りに行ける。

## Consequences

- Pi 側は素の Pi のままなので、エージェントの定義を Pi の流儀で書け、Pi のエコシステムの拡張やスキルをそのまま使える。
- context ごとにプロセスが分かれるので、1 つの context の障害が他に及ばない。その代わり、context ごとに起動の時間とメモリが掛かる。
- アダプタと Pi の間は RPC になる。Pi の RPC の形が変わると、アダプタの追従が要る。
- ポーリングは、クラスタの外や NAT の内側からでも使える。結果が出てから呼び出し元が気づくまでに、ポーリングの間隔ぶんの遅れが出る。
- 他の呼び出し元の context を続けたり覗いたりできないので、呼び出し元どうしで文脈が混ざらない。
- Task の状態を永続化するための仕組み（SDK に無い部分）を自分で作ることになる。
- なつみと汎用ホストで Pi の版が分かれる。なつみの側の Pi を上げるのは、なつみの側の作業として残る。
