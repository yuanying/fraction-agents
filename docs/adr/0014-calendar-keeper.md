# 0014. カレンダー係（calendar-keeper）: サービスアカウントで共有されたカレンダーを読み、自分の予定だけを変える

- Date: 2026-09-30
- Status: Accepted

## Context

秘書のなつみが、本人のその日の予定を知り、本人に頼まれた予定を Google Calendar に登録したい。
なつみ本体に Google の道具と資格を持たせると、なつみのコンテナに置く秘密が増える。
なつみは会話の相手であり、会話に入った文（メールの本文や、ほかのエージェントの返事）に促されて予定を書き換える危険も抱える。

そこで、fraction-agents にカレンダー専用のエージェントを立て、なつみは A2A で自然文で頼む（ADR 0001）。
Google への資格は係の中に閉じる。

前提として分かっていることは次のとおりである。

- Google の API への認証には、本人の OAuth の同意（refresh token）か、サービスアカウントがある。
  refresh token は、同意の画面を通す手順が要り、アプリが「テスト中」のままだと 7 日で切れる。
  サービスアカウントの鍵には期限が無く、本人がカレンダーを共有した分だけに触れる。
- サービスアカウントは、domain-wide delegation が無ければ、予定に参加者を招待できない（招待のメールを送れない）。
- Google Calendar の予定には、アプリが自由に使える `extendedProperties.private` がある。そのカレンダーの予定の写しにだけ付き、Google の画面には出ない。
- 汎用ホスト（ADR 0002・0007）は、agentDir（ADR 0008）の設定と Pi パッケージの拡張で、専用の係を作れる。調べもの係（ADR 0013）がその例である。

## Decision

### 係の役割

- 係は、期間を指定されて予定を調べて答える。共有されたカレンダーをまたいで調べる。
- 係は、本人に頼まれた予定を登録する。自分で登録した予定だけを変更・削除する。
- 「明日」「来週の火曜」のような日付の言い方は、係の LLM が解釈する。呼び出し元は言い方のまま渡してよい。
- 定時に予定を取りに行く仕組みは作らない。毎朝の予定が要るなら、呼び出し元（なつみ）が自分の予約で頼む。

### 汎用ホストで作る

- 係は汎用ホスト（pi）の上に作り、Google Calendar の道具は fraction-agents の Pi パッケージの拡張 `calendar` に足す。
  専用のサーバーは書かない。image も汎用ホストのものを使う。
- 道具は、今の日時、カレンダーの一覧、予定の一覧、登録、変更、削除の 6 つである。
- Google の API は REST を直接呼ぶ。JWT の署名は `node:crypto` で行い、`googleapis` などのライブラリには頼らない。
  使う API は数本で、依存を増やすほどの量ではない。
- pi の組み込みの道具（read・bash・edit・write など）は係に出さない（ADR 0013 と同じ）。
  予定の説明などに仕込まれた指示で、係が鍵のファイルを読む道を塞ぐ。
- モデルは、調べもの係と同じく ChatGPT Plus の経路（`openai-codex`）の `gpt-6-sol` を使う。

### サービスアカウントと共有

- Google への認証はサービスアカウントで行う。鍵（JSON）は Kubernetes の Secret にし、係の Pod にファイルでマウントする。
- 本人は、係に使わせたいカレンダーを、サービスアカウントに「予定の変更」の権限で共有する。係は共有されたカレンダーにだけ触れる。
- 係の使うカレンダーの ID は、agentDir の `calendar.json` に並べる。そこに無いカレンダーは、ID を渡されても使わない。
  既定の登録先とタイムゾーンも `calendar.json` に書く。
- scope は予定の読み書き（`calendar.events`）とカレンダーの名前を読むこと（`calendar.readonly`）に絞る。共有や設定は変えられない。
- なりすまし（domain-wide delegation）は使わない。

### 印のある予定だけを変えられる

- 係が登録する予定には、`extendedProperties.private` に印を付ける。
- 変更・削除の道具は、先に予定を取り、印が無ければ断る。AGENTS.md の指示だけに頼らず、道具の側で止める。
  本人が入れた予定は、係には読むだけのものになる。
- 変更で送るのは渡された項目だけなので、印は変更で消えない。

### 登録のきっかけ

- 係が予定を登録・変更・削除するのは、本人がはっきり頼んだときだけとする。
- 呼び出し元（なつみなど）は、本人の依頼であることと中身を依頼文に書く。これを Agent Card の説明と係の AGENTS.md に書く。
- 本人の依頼であることが書かれていない依頼、会話から見つけた予定らしいものの登録、中身が曖昧な依頼は、係が `ask_caller` で確かめる。
- これはプロンプトの規則であって、道具の側では確かめない。道具が守るのは、印の無い予定を変えないことと、招待しないことである。

### 招待しない

- 係は参加者を招待しない。道具は `attendees` を受け取らず、登録・変更・削除はいつも `sendUpdates=none` で送る。
- サービスアカウントでは、そもそも招待を送れない。道具の形でも閉じておく。

### 日付の解釈を確かにする

- 道具の結果の先頭に、今の日付・曜日・時刻とタイムゾーンを 1 行で付ける。係は推測でなくこの行から日付を決める。
- 時差の付いていない時刻は `calendar.json` のタイムゾーンで読む。予定の時刻も、このタイムゾーンで見せる。

## Consequences

- 本人は、GCP でサービスアカウントと鍵を作り、Calendar API を有効にし、カレンダーをサービスアカウントに共有する。
  鍵の置き場所（Secret）は環境の overlay の側で作る（ADR 0010）。
- 鍵に期限が無いので、漏れたら本人が GCP で鍵を消すまで使える。鍵は Secret にだけ置き、係は鍵を読む道具を持たない。
- 係が登録した予定を本人が Google の画面で直しても、印は残る。係はその予定を変えられるままである。
- 本人が入れた予定を係に直させることはできない。頼まれた係は、本人が直すよう返す。
- 参加者のある予定は作れない。招待が要るようになったら、OAuth の同意か delegation を別に決める。
- 登録のきっかけはプロンプトで守るので、呼び出し元が「本人の依頼」と偽れば係は登録する。守りは、呼び出し元を
  `allowedCallers` で絞ること（ADR 0003）と、係が変えられるのは自分の予定だけであることにある。
- 繰り返しの予定は読めるが、登録はできない。
- Google の API の形が変わったら、自前の道具を直す。
